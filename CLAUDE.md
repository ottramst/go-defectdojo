# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

`github.com/ottramst/go-defectdojo` is a hand-written, idiomatic Go client for the [DefectDojo](https://github.com/DefectDojo/django-DefectDojo) REST API v2 (single package `defectdojo`, Go 1.26+, one dependency: `go-querystring`). It is pre-1.0. Breaking changes are allowed but must be listed under `BREAKING CHANGES` in `CHANGELOG.md`.

Its main consumer is [terraform-provider-defectdojo](https://github.com/ottramst/terraform-provider-defectdojo), so v1.0 scope is DefectDojo's configuration objects: product types, products, engagements, SLA configurations, users, notifications, notification webhooks, Jira instances and projects, system settings, and lookup objects (regulations, note types, development environments, announcements, CI/CD infrastructure, product platforms/lifecycles/origins, test types). Runtime data (findings, tests, imports, risk acceptances) is backlog. Work is planned as GitHub milestones (v0.1.0 to v1.0.0) with one epic issue per area and one sub-issue per service. The OpenAPI schema is the reference, but the code is hand-written, not generated.

The client supports and tests the latest patch of the two newest DefectDojo minors (currently 3.5.103 and 3.4.304), listed in `.github/defectdojo-versions.json`. DefectDojo renames and retypes fields in minor releases (3.2 renamed the engagement CI/CD fields, 3.3 turned product platform/lifecycle/origin into lookup tables, 3.6 removes the tool configuration endpoints), so check new code against both versions. 2.x is not supported: 3.0 removed the role-based access endpoints (groups, members, roles) from the open-source edition.

## Common Commands

```bash
make default     # fmt, lint, test
make build       # go build ./...
make fmt         # gofmt -s
make lint        # golangci-lint (v2 config, zero tolerance)
make test        # unit tests
make up          # start DefectDojo (DD_VERSION defaults to the newest supported)
make testacc     # unit + acceptance tests (needs `make up`, DEFECTDOJO_ACC=1)
make contract    # check the types against the supported versions' OpenAPI schemas
make coverage    # download the schemas to .cache/ and regenerate COVERAGE.md
make down        # stop the stack and delete its data
```

Run a single test:
```bash
go test -v -run TestProductTypesService_Patch ./...
DEFECTDOJO_ACC=1 go test -v -run TestAccProductTypes ./...
```

## Running Acceptance Tests Locally

```bash
make up                        # DefectDojo 3.5.103 on localhost:8080, about 30 seconds
# make up DD_VERSION=3.4.304   # the other supported version (make down first)
make testacc
make down
```

The compose stack is PostgreSQL 18 (tmpfs), Valkey, a one-shot `initializer` (migrations, admin user, fixtures), `uwsgi`, and DefectDojo's `nginx` on `127.0.0.1:8080`. Celery is left out (the API doesn't need it) and `DD_ASYNC_OBJECT_DELETE` is off, so deletes are synchronous. Don't publish uwsgi's own HTTP router (port 8081): it is meant for liveness checks, and with it the writes after the first request failed with `EOF` in CI (observed, consistent with dropped keep-alive connections; Go retries only idempotent requests). The nginx image has `wget` but no `curl` in 3.5. The superuser is `admin` / `DefectDojoAcc1!`. Tests read `DEFECTDOJO_URL`, `DEFECTDOJO_API_TOKEN` or `DEFECTDOJO_USERNAME`/`DEFECTDOJO_PASSWORD`, falling back to those defaults. Fixtures that the initializer loads: the product type "Research and Development" (id 1, null timestamps), the SLA configurations "Default" (id 1) and "No SLA Enforced" (id 2), development environments, regulations and test types.

## Architecture

**Client core (`defectdojo.go`, `request.go`, `errors.go`, `pagination.go`, `nullable.go`):**
- `NewClient(baseURL, ...ClientOption)`. Options: `WithAPIToken` (`Authorization: Token <t>`), `WithBasicAuth`, `WithHTTPClient`, `WithUserAgent`. The base URL keeps any path prefix and loses its trailing slash. The default `http.Client` has no timeout; contexts govern. The User-Agent is `go-defectdojo/<module version>`, read from build info.
- **Redirects are not followed.** `withoutRedirects` copies the HTTP client (also one passed to `WithHTTPClient`, unless it has its own `CheckRedirect`) and returns the 3xx response, which `CheckResponse` turns into an `*ErrorResponse` naming the `Location`. DefectDojo redirects paths without a trailing slash (301), and following would turn writes into reads.
- Services use the go-github pattern: `type ProductTypesService service`, all sharing `Client.common`. A new service needs a field on `Client` and a line in `initServices()`.
- `NewRequest(ctx, method, path, body, ...RequestOption)`: `path` is the literal API path (`/api/v2/.../`) with its trailing slash, segments already escaped and an optional `?query`. Paths with a `#` or unescaped characters are rejected. Headers: `Accept`, `Content-Type` (JSON bodies only), `User-Agent`, `Authorization`, then the caller's options. An `io.Reader` body is sent raw.
- `Do(req, v)`: non-2xx returns `*ErrorResponse`. `v == nil` drains the body, an `io.Writer` gets it raw, anything else is JSON-decoded; an empty body (204) leaves `v` untouched; data after the JSON value is an error.
- Helpers (`request.go`): `addQuery(path, opt)` encodes `url:"..."` tags with go-querystring; `WithQueryParam` appends without re-encoding; `requirePositive(name, id)` rejects IDs ≤ 0 so no request goes to a list endpoint by mistake; `orNull(v)` (nil for a zero value, sent as `null`), `orEmpty`/`orEmptyPtr` (nil slices sent as `[]`); `Client.count(ctx, path, filter, opts)` reads a `limit=1` count, and `missingFilterObject(err, filters...)` turns a 400 on a foreign-key filter (an ID that doesn't exist) into an error that also matches `ErrNotFound`.
- `ErrorResponse{StatusCode, Message, Fields, Body}`. `Message` is the body's `message`, else its `detail`; a body that is a bare JSON string or list of strings becomes the message. `Fields` holds the other keys whose values are a string or a list of strings (DRF validation errors, including `non_field_errors`); the `pro` advertisement key is dropped. `Is()` maps 400/401/403/404/409/423/429 to the sentinels. Non-JSON bodies become `Message`, cut to 512 bytes.
- `paginate` (offset pagination over `{count, next, results}`) backs every `ListAll` iterator: lazy, restartable, yields an error once and stops, stops on an empty page. `ListOptions{Limit, Offset}` is embedded in list option structs.
- `Nullable[T]` (`Value(v)`, `Null[T]()`) is for nullable fields of `…Patch` structs, tagged `omitzero`: left out, `null`, or a value.

**Service conventions** (`product_types.go` is the template):
- Method names: `List`, `ListAll`, `Get`, `GetByName`, `Create`, `Update` (PUT), `Patch` (PATCH), `Delete`, `DeletePreview`. Other operations are named after the endpoint.
- Signatures: `(ctx, id int, body/options, ...RequestOption) (*T, *Response, error)`, or `(*Response, error)` without a body. IDs are DefectDojo's integer IDs.
- Every method that calls one endpoint ends its doc comment with `// DefectDojo API: METHOD /api/v2/path/{id}/`, matching the schema path exactly; `tools/coverage` parses it (and godot ignores it). Helpers that read another service's endpoint, like `CountProducts`, name the endpoint in prose instead.
- One exported type per object for reads and writes (`ProductType`), with JSON tags. `Create` and `Update` send an unexported `…Request` struct with only the writable fields, built by `new…Request`, which validates required fields and never mutates the caller's value. `Update` sends every writable field, so `""` clears text and a nil slice becomes `[]`. Zero values must never reach DefectDojo as invalid values: nullable fields whose zero value isn't a valid value (lookup slugs with `minLength: 1`, enums without `""`, foreign keys) are `*T` without `omitempty` in the request, set with `orNull` (sent as `null`); non-nullable foreign keys with a server default (`sla_configuration`) are `omitempty`; nullable numbers where 0 is meaningful (`user_records`) are pointers on the read type and `omitempty` in the request, so nil keeps the current value (clear them with PATCH). Exceptions, where `null` would not mean "unset": enums whose `null` resets them to a default (engagement `status` and `engagement_type`) are `omitempty`, so `Update` keeps them when empty; tags that can be inherited (engagements) are `omitzero`, so nil `Tags` are left out (a new engagement inherits, `Update` keeps them) and an empty non-nil slice is sent as `[]`. The contract test fails if a pointer or `Date` sent as `null` isn't nullable, unless the contract lists it in `nonZero` (the constructor rejects zero). `…Patch` structs use pointers with `omitempty` for non-nullable fields and `Nullable[T]` with `omitzero` for nullable ones.
- Nullable strings in responses decode as `""`; nullable timestamps as the zero `time.Time` (`omitzero`).
- `GetByName` lists with the name filter and re-checks for an exact match on the client side, returning an error that matches `ErrNotFound`. Filters vary by endpoint (`name` is exact and case-sensitive on product types; on products `name` is a case-insensitive contains match and `name_exact` a case-insensitive exact one).
- Every type the client sends or decodes is listed in `contracts` in `contract_test.go`.

**DefectDojo API quirks** (verified against 3.4.304 and 3.5.103):
- Authentication: a missing or invalid token is **403** (`{"detail": "Invalid token."}`), not 401. Basic auth always works; tokens only when `DD_API_TOKENS_ENABLED`. `POST /api/v2/api-token-auth/` returns `{"token"}`, the same token every time.
- Paths need their trailing slash: without it, 301 to the slashed path.
- Errors: 404 is `{"detail": "No Product_Type matches the given query."}`. 400 is a field map plus a sentence-form `message` (3.4.300+) and a `pro` advertisement. A duplicate unique name is a **400** with a field error, not a 409; 409 means a delete blocked by a reference, or a race (a `PROTECT` reference, as from Jira projects to their instance, is a 500 instead).
- Unknown request fields are ignored, not rejected.
- Text fields are stored with leading and trailing whitespace removed: DRF's `CharField` trims with Python's `str.strip`, which also removes Unicode whitespace such as U+00A0, U+3000 and U+2028, but not zero-width characters (U+200B, U+FEFF). A whitespace-only required field (`name`) is a 400 "may not be blank"; a whitespace-only optional one (`description`) is stored as `""`. `max_length` counts Unicode code points (`utf8.RuneCountInString`), not bytes. The client sends values as given; callers that compare what they sent with what they read back, like the Terraform provider, must account for it. Verified on product type `name` and `description` (3.5.103); serializers can turn trimming off, so check each new service's fields.
- PUT keeps fields that are left out (only `name` is required on product types); PATCH changes only what is sent. `null` clears nullable fields; `authorized_users: null` is a 400, `[]` clears it.
- Product types: `name` is unique, case-sensitive; `?name=` is an exact, case-sensitive match. `description` is nullable and stored as given (`""` and `null` differ). `created`/`updated` are null for fixtures. `archived_at`/`archive_batch` exist from 3.5 (DefectDojo Pro archiving) and are always null in the open-source edition.
- **Deleting a product type deletes its products** with their engagements, tests and findings, and answers 204. `delete_preview` lists every object a delete removes, the object itself and M2M rows (`Product_Type_authorized_users`) included; on 3.4 it loads the whole tree. `GET /api/v2/products/?prod_type={id}&limit=1` counts the products cheaply.
- Products: `name` is unique case-sensitively, so "Foo" and "foo" can coexist; `?name=` is `icontains` and `?name_exact=` is `iexact` (case-insensitive), so `GetByName` re-checks on the client side. `name` and `description` are trimmed; a whitespace-only `description` is a 400. `platform`, `lifecycle` and `origin` are slugs of lookup tables (`""` is stored as null, an unknown slug is a 400); seeded values: platform `web service`, `desktop`, `iot`, `mobile`, `web`; lifecycle `construction`, `production`, `retirement`; origin `third party library`, `purchased`, `contractor`, `internal`, `open source`, `outsourced`. `business_criticality: ""` is stored as `""`. A user or SLA configuration ID of 0 is a 400 (invalid pk). `sla_configuration` defaults to 1. Users and SLA configurations referenced by products can't be deleted (409).
- **The SLA lock:** changing an SLA configuration's days or `enforce_*` fields sets `async_updating` on the configuration and on every product using it, and changing a product's `sla_configuration` sets it on the product and on the **new** configuration (creating a product with a configuration sets nothing). Each queues a Celery task that recalculates the findings' SLA dates and clears the flags. While a configuration is flagged, a change of its days or `enforce_*` fields is a 400 ("Finding SLA expiration dates are currently being calculated. The SLA days for this SLA configuration…"); while a product is flagged, a change of its `sla_configuration` is a 400 ("…currently being recalculated. The SLA configuration for this product…"), both in `non_field_errors`; `IsSLARecalculating` matches both. Sending the current values again is fine, and `name`, `description` and `restart_sla_on_reactivation` are never locked; a locked configuration can still be deleted. **The task returns without clearing the flags when the system setting `enable_finding_sla` is off**, so such servers stay locked for good. The test stack has no Celery worker, so the flags never clear there: change a configuration's days, or a product's SLA configuration, at most once per test, on objects the test created.
- SLA configurations: `name` is unique, case-sensitive, and trimmed; there are no list filters. `description` stores `""` as `""` and `null` as `null`. The API doesn't call the model's `clean()`, so days of 0 or below are accepted (the UI requires at least 1). Deleting "Default" (id 1) is a 400 ("Unable to delete default SLA Configuration."), and deleting a configuration that a product uses a 409.
- **Tags** (products, engagements; 3.4.304 and 3.5.103): despite `force_lowercase` on the models, the API keeps a tag's case, but a tag takes the spelling of an existing tag of the same kind (product tags or engagement tags) that matches it ignoring case, and case variants within one list collapse into the first. Commas split a tag; a space, `'` or `"` is a 400 (a non-breaking space is accepted); an empty tag is dropped; over 255 characters is a 500. Write responses can list a tag twice (a GET doesn't).
- Engagements: `name` is nullable and not unique, but can't be empty: an engagement created or updated (PUT or PATCH) with a `null`, `""` or missing name is **named after its `target_start`** (`"2026-01-05"`). `?name=` is an exact, case-sensitive match. Text fields are trimmed; optional text and URL fields keep `""` as `""` and read `null` when never set; a whitespace-only `description` becomes `""`. Dates are `YYYY-MM-DD`, but DefectDojo also accepts `2026-1-5` and `20260105` and returns them normalised. `target_start > target_end` is a 400 only on POST (PUT and PATCH accept it); `target_start: null` is a 400. `status: null` heals to `Not Started` (and `engagement_type` to `Interactive`); `""` is a 400. `active` is read-only: `POST …/close/` sets `Completed` and inactive, `…/reopen/` `In Progress` and active (both answer 200 `{}`); PATCHing `status` leaves `active` alone. Moving an engagement to another product (PUT/PATCH `product`) re-homes its endpoints but not its tags. **Every import into a `CI/CD` engagement moves `target_end` to the scan date when that is later** (`dojo/importers/base_importer.py`).
- **Tag inheritance** (a product's `enable_product_tag_inheritance`, or the system setting): the product's tags are added to its engagements, and the response doesn't say which are inherited (`inherited_tags` is not exposed). A write of other tags without the inherited ones gets them back, but **an empty list removes them all**, and an engagement created with `tags: []` inherits nothing (left out, it inherits). A change to the product's tags reaches its engagements through Celery (`countdown=5`), so never in the test stack.
- `GET /api/v2/tests/?engagement={id}&limit=1` counts an engagement's tests; tests need `engagement`, `test_type` (fixtures: 1 "API Test"), `title`, `target_start` and `target_end` (date-times).
- Foreign-key list filters such as `/api/v2/engagements/?product={id}` reject IDs that don't exist with a 400 field error ("Select a valid choice"); number filters such as `/api/v2/products/?prod_type={id}` return 0.
- `GET /api/v2/user_profile/` returns the authenticated user and its `user_contact_info`, which is null for users without one (such as the initializer's admin) although the schema doesn't mark it nullable; `user_contact_info.user_profile` repeats the user.
- Users (superuser, or the configuration permissions for users): `username` is unique case-sensitively ("alice" and "ALICE" coexist), trimmed, and letters (Unicode), digits and `@.+-_` only; `email` is required, not unique, and `""` is a 400; `first_name`/`last_name` are trimmed and not nullable (`null` is a 400, clear them with `""`). The `username`, `email`, `first_name` and `last_name` filters are `icontains`. A POST needs a `password` unless `DD_REQUIRE_PASSWORD_ON_USER` is off ("Passwords must be supplied for new users"); it must pass the password rules of the system settings (by default at least 9 characters with a digit, an uppercase letter and a special character) and is trimmed. **A password in PUT or PATCH is a 400** ("Update of password though API is not allowed"). Users created through the API have no `user_contact_info`, can get a token from `api-token-auth` right away, and get a notifications row (cloned from the template row if there is one). `configuration_permissions` takes permission IDs from `/api/v2/configuration_permissions/` (superuser only; exact `codename` and `name` filters; database IDs that differ between installations; the jira_instance, github_conf, engagement_survey and question permissions are listed only when Jira, GitHub or questionnaires are enabled); an unknown or non-configuration ID is a 400 "Invalid pk"; a non-empty list replaces the configuration permissions and keeps the user's other Django permissions, but **`[]` removes all of them**, and a left-out field keeps them. Only superusers may change staff, superuser and configuration permissions, and the `username` or `email` of another user. Deleting yourself is a 400 whose body is a bare JSON string (`"Users may not delete themselves"`); deleting a user that other objects refer to (`RESTRICT`) is a 409, for example: findings it reported or imported (`reporter`, `mitigated_by`, `last_reviewed_by`, the review requests), tests and engagements it leads, risk acceptances it owns, products naming it (`product_manager`, `technical_contact`, `team_manager`), finding groups it created, endpoint statuses it mitigated, surveys it answers, so a CI service account usually can't be deleted, only deactivated; a delete takes the user's notifications row, alerts and owned notification webhooks with it. `POST …/reset_api_token/` (no body, 204, despite the schema's request body and 200 `User`) replaces the user's token, creates its `user_contact_info` and notifies it; on yourself it is a 400 whose body is a JSON list of strings.
- Notification webhooks (superuser): `name`, `url`, `header_name` and `header_value` are trimmed; `name` is unique case-sensitively, `url` a URL (any scheme Django's `URLField` accepts, `ftp` included) of at most 200 characters; the schema requires neither, and a POST without them stores `""`. `header_name`/`header_value` store `""` as `""` and `null` as `null`, and **`header_value` is returned in plain text** (and is an exact list filter). `status`, `first_error`, `last_error` and `note` are read-only (`editable=False`): a PATCH of them is ignored, so a webhook DefectDojo marks `inactive_permanent` can't be reactivated through the API. Celery workers set them when deliveries fail (`inactive_tmp` on a 5xx, 429 or timeout, `inactive_permanent` on a 4xx, a connection error or a day of errors), and the UI when a webhook is deactivated or edited (editing reactivates it). Every field is an exact list filter; an unknown `status` or `owner` is a 400. **The list is unordered** (no `order_by`, no ordering filter), so offset pages aren't stable while webhooks change. `owner` (a user, null for a system webhook) cascades: deleting the user deletes its webhooks. The API doesn't send a test request on create.
- Notifications (superuser; the client's `NotificationSettings`): a row's scope is `(user, product, template)`: system-wide `(null, null, false)`, the template `(null, null, true)`, personal `(user, null)`, per product `(user, product)`. DefectDojo `get_or_create`s the system row when it sends a notification, and creates a personal row for each new user (copied from the template when there is one); a `(null, product)` row is never used. A second row for a scope is a 400 ("…must make a unique set" or "Notification for user and product already exists"). The list filters are `user`, `product` and `template` (exact; no null filter; an unknown user or product is a 400 "Select a valid choice"); the list is ordered by ID. The 17 events are `MultipleChoiceField`s of `slack`, `msteams`, `mail`, `webhooks`, `alert`, defaulting to `["alert"]` (stored as `"alert,alert"`); duplicates collapse and `[]` means none. **`scan_added_empty` is not declared on the serializer**, so DRF makes it a single `ChoiceField`: a write takes one channel as a string or `""` (a list is a 400 "not a valid choice"), the write's response holds the string, and a GET reads a list; the schema says `string` (the `specBug` exception in `contract_test.go`). **A PUT resets what it leaves out**: the 17 events to `alert`, `user`/`product` to null, `template` to false; it keeps a left-out `scan_added_empty` (no serializer default), so the client always sends it. A POST or PUT with `template: true` is a 400 ("Notification template already exists") whenever a template exists, the template itself included; a PUT of the template without `template` turns it into a duplicate system row, which DefectDojo deletes the next time it sends a notification. Only PATCH is safe for the template. Deleting a user's personal row silences the user (superusers excepted); deleting a user deletes its rows.
- System settings (superuser): a single object (the stack's has ID 1) that `GET /api/v2/system_settings/` lists; a GET by ID, POST and DELETE are 405. No request field is required, so a PUT keeps what it leaves out, like a PATCH (the client has only `Patch`). `slack_token`, `msteams_url` (an incoming webhook URL with its token) and `jira_webhook_secret` (a UUID DefectDojo generates on installation) are returned in plain text. `jira_webhook_secret` is nullable but not blank (`""` is a 400, `null` clears it); `jira_labels` and `jira_minimum_severity` take both `null` and `""`; the other text settings aren't nullable (`null` is a 400, `""` clears them). Text settings are trimmed. `max_dupes` and the risk acceptance days are nullable (`max_dupes: null` means no limit, 0 deletes every duplicate). Field validators run (password lengths 9 to 48), but the model's `clean()` doesn't, so a minimum length above the maximum is accepted (its own message has them backwards). Settings are cached per request, so a change is seen by the next request. `read_only_mode` (3.5.100+; older servers ignore it in a write) makes every unsafe request except to `api/v2/system_settings/` and `api-token-auth` a **423** `{"detail": "Read-only mode is on. …"}` (`ErrLocked`); inbound webhooks get a 503 instead. `install_id` (read-only) is in both versions.
- Jira instances (superuser, or the `*_jira_instance` configuration permissions, listed only while `enable_jira` is on): also served as `/api/v2/jira_configurations/`. The list filters are `id` and `url` (exact; no name filter), ordered by ID. `configuration_name` isn't unique and defaults to `""` when left out, but `""` sent is a 400 ("may not be blank"), as is `default_issue_type: ""` (default `Bug`; the choices come from `JIRA_ISSUE_TYPE_CHOICES_CONFIG`, extended by `DD_JIRA_EXTRA_ISSUE_TYPES`); the five severity mappings can't be blank; zero IDs (`epic_name_id`, the status keys) are accepted. `password` is write-only: a POST and a PUT need it, a PATCH without it keeps the stored one unless `url` changes (400 `{"password": ["This field is required when changing the URL."]}`), and a URL that differs only in a trailing slash isn't a change (it is stored as sent). Text is trimmed. DefectDojo contacts nothing when an instance is created or changed (any URL works, `localhost` included), and `enable_jira` doesn't matter. **Deleting an instance that Jira projects use is a 500** (`JIRA_Project.jira_instance` is `PROTECT`, and the exception handler maps only `RestrictedError` and unique violations to 409), and `delete_preview` lists only the instance: `GET /api/v2/jira_projects/?jira_instance={id}&limit=1` counts the projects (an unknown instance is a 400 "Select a valid choice"; the list includes only projects the caller may view).
- Jira projects (edit permission on the product or engagement, no superuser; reads are filtered to what the caller may view): also served as `/api/v2/jira_product_configurations/`. Exactly one of `product` and `engagement` (400 "Either engagement or product has to be set."; a PATCH checks the merged result). `product` isn't unique, so a product can get several configurations (DefectDojo's helpers use one); `engagement` is one-to-one, so a second is a 400 on `engagement` ("jir a_ project with this engagement already exists.", which also wins over the scope check). A product or engagement that doesn't exist is a **404** (the permission check looks it up before the serializer). `jira_instance` is nullable and a POST without it is accepted (only the UI requires one). `project_key` and `component` (comma-separated) aren't nullable (`""`); `default_assignee`, `jira_labels` and `issue_template_dir` are. `custom_fields`, `close_transition_fields` and `reopen_transition_fields` are nullable JSON of any shape (a JSON string is parsed first); a write's response keeps the request's key order, a GET returns the keys sorted (jsonb). Text is trimmed (a whitespace-only `default_assignee` becomes `""`). `issue_template_dir` takes any string (only the UI limits it to the template folders). `epic_issue_type_name` defaults to `Epic` when left out (`""` sent is stored as `""`), `enabled` to true. `suppress_sla_notification_comments` (3.5.103+; older servers drop it) can't be true with `product_jira_sla_notification` (400; 3.4 accepts both). `archived_at`/`archive_batch` exist from 3.5.0. Filters: `id`, `jira_instance`, `product`, `engagement`, `project_key`, `component`, `enabled`, `push_all_issues`, `enable_engagement_epic_mapping`, `push_notes` (no name filter). Deleting the product or engagement deletes its configurations; deleting a configuration deletes its `JIRA_Issue` links (cascade), which `delete_preview` lists. `enable_jira` doesn't matter for the API.
- Regulations (reads for any user; writes need the `*_regulation` configuration permissions): `name` (≤128) and `acronym` (≤20) are each unique (a duplicate is a 400 on the field, "regulation with this name already exists."), `jurisdiction` (≤64) and `category` (`privacy`, `finance`, `education`, `medical`, `corporate`, `security`, `government`, `other`) are required; `description` and `reference` (a URL; anything else is a 400) are optional and store `""`. Text is trimmed. The list filters are `id`, `name` and `description` (exact, case-sensitive; no acronym filter), ordered by ID. The fixtures seed 26 (`PCI DSS`, `HIPAA`, …). Products refer to them through an M2M, so deleting a regulation silently removes it from every product; `delete_preview` lists only the regulation.
- Note types (superuser, or the note type configuration permissions; `/api/v2/note_type/`, singular): `name` (≤100) is unique (400 "note_ type with this name already exists."), `description` (≤200) is required (`""` is a 400). `is_active` and `is_mandatory` default to **true**, `is_single` to false. An active mandatory type keeps the UI (not the API) from closing findings, tests and products until they have a note of the type; `is_single` allows one note of the type per object. Filters: `id`, `name`, `description`, `is_single`, `is_active`, `is_mandatory`. The notes API (`POST /api/v2/tests/{id}/notes/`) takes any type, inactive ones included. **Deleting a note type deletes its notes** (`CASCADE`); `/api/v2/notes/` has no `note_type` filter, and `delete_preview` lists the note type, each note (`Notes`), the M2M rows of their history (`Notes_history`) and of their objects (`Test_notes` and the like), so only `Notes` entries count.
- There is no version endpoint: `info.version` of `GET /api/v2/oa3/schema/?format=json` (about 860 KB, served without authentication) is the only source.

**Tooling:** `tools/coverage/` is a separate module, so the library keeps one dependency. It parses the `oas.json` release assets in `.cache/specs/` (JSON, read as YAML) and the `// DefectDojo API:` annotations, then writes `COVERAGE.md`. It fails on malformed annotations, annotations that match no schema, are not on a method, or are duplicated. Versions are passed oldest first. Endpoints that DefectDojo serves twice (`jira_configurations` for `jira_instances`, `jira_product_configurations` for `jira_projects`) are listed in its `aliases` map, and their rows name the endpoint and method they repeat.

## Test Patterns

- Unit tests are in package `defectdojo_test` and use the standard library only (no testify). Assertions read `t.Errorf("X = %q, want %q", got, want)`.
- Helpers in `helpers_test.go`: `setup(t)` returns `(*http.ServeMux, *defectdojo.Client)` against an `httptest.Server`; `testHeader`, `testQuery`, `testJSONBody` (semantic JSON comparison), `fixture(t, "product_types/get.json")`, `writeJSON`.
- Register handlers with method patterns (`mux.HandleFunc("PATCH /api/v2/product_types/4/", ...)`), so a wrong path (404) or method (405) fails the test.
- Cover for each method: the happy path and the exact request body; read-only fields are not sent and the caller's value is not mutated; error mapping; ID and nil-body guards.
- Fixtures in `testdata/` are **captured from real DefectDojo responses** (curl against the compose stack).
- Acceptance tests (`*_acc_test.go`, `TestAcc*`): use `accClient(t)`, which skips unless `DEFECTDOJO_ACC` is set and never skips after that. Name objects with `randName(t, "acc")` and remove them in `cleanup(t, ...)`. Each test runs a full lifecycle: create, duplicate, get, get by name, read-modify-write update, patch, list, delete, then get returning `ErrNotFound`.
- Behavior that only some supported versions have is checked by version inside the test (`client.ServerVersion` and `compareVersions` from `contract_test.go`: it strips suffixes such as `-dev`, so that `3.6.1-dev` compares as `3.6.1`; exported as `CompareVersions` in `export_test.go`): assert it where the version has it, and its absence elsewhere. Don't skip: `accClient` never skips once `DEFECTDOJO_ACC` is set.
- `contract_test.go` (package `defectdojo`, so it sees the unexported request types) runs when `DEFECTDOJO_SPEC_DIR` is set (`make contract`). It checks each listed type's JSON fields against its schema component: the property exists, its primitive type and nullability match, request fields are writable, and every required property is sent. Fields newer versions added go in `since`. Properties whose schema type is wrong go in `specBug`, with the reason; the test fails once the schema is fixed. `DEFECTDOJO_SPEC_VERSIONS` overrides the versions (the canary uses `nightly`, which counts as newest).
- `example_test.go` holds compile-only `Example*` functions (no `// Output:`).

## CI

GitHub Actions workflows in `.github/workflows/`:
- `main.yml` ("CI/CD") calls the reusable `lint`, `build`, `test` and `coverage` workflows. The single `CI gate` job is the required status check.
- `build`: go.mod tidy check, build, vet, and race-enabled unit tests on Go 1.26.x and 1.27.x. The go.mod `go` directive is the oldest one.
- `test`: a `versions` job reads `.github/defectdojo-versions.json` (and checks that every DefectDojo image in `docker-compose.yml` is tagged `${DD_VERSION:-<newest>}`), then the acceptance tests run on each version via `docker compose up -d --wait` with `DD_VERSION` from the matrix.
- `coverage`: tests the coverage tool, runs `make contract` and `make coverage`, and fails if `COVERAGE.md` changed.
- `upstream.yml` (scheduled, not in the CI gate): the nightly `canary` runs the acceptance tests and the contract test (against the served schema) on the `nightly-dev` image; the `release-watch` job opens a `type/chore` issue on Mondays when DefectDojo has a newer minor release than the newest supported one.
- Also: CodeQL, govulncheck and dependency review (`security.yml`), OpenSSF Scorecard, actionlint plus zizmor for workflow changes (reusable workflows are called with `./` paths plus `# zizmor: ignore[self-repository]`), lock threads, and waiting-response triage.
- `release.yml`: pushing a `vX.Y.Z` tag creates the GitHub release from the `## vX.Y.Z` section of `CHANGELOG.md` (the heading must match exactly), in the `release` environment, which only allows `v*` tags. A `warm-proxy` job then warms proxy.golang.org. Never push a throwaway tag to test it: proxy versions cannot be removed.
- All actions are pinned to commit SHAs with a version comment. Workflows use top-level `permissions: {}` or `contents: read` and grant more per job. Every job has a timeout, and checkouts use `persist-credentials: false`.
- Never commit downloaded files: `.cache/` (the schemas) must stay in `.gitignore`.

## Rules

- Add a `CHANGELOG.md` entry under `## Unreleased` for user-visible changes (HashiCorp style: `BREAKING CHANGES`, `FEATURES`, `ENHANCEMENTS`, `BUG FIXES`, `NOTES`), linking the issue.
- Every new service method needs the `// DefectDojo API:` annotation, unit tests, an acceptance test on both supported versions, its types in `contracts`, and a regenerated `COVERAGE.md` (`make coverage`).
- Pull request titles follow Conventional Commits (`feat(products): ...`, `fix(product-types)!: ...`). PRs are squash-merged and reference their issue (`Closes #N`).
- Keep the library to the standard library plus go-querystring. Tooling dependencies belong in `tools/`.
- Record newly discovered DefectDojo API quirks in the "DefectDojo API quirks" section above.
- Plans for a milestone, or for any change that spans several pull requests, go through the `plan-critic` subagent (`.claude/agents/plan-critic.md`) before they are approved. Spawn it with the plan file path and the decisions the user has made only, fold the confirmed findings into the plan, and note in the plan which were taken. Run it again if the findings change the plan's structure, such as its pull requests or their order.
- Every pull request, including Dependabot and release pull requests, gets an independent review by the `pr-reviewer` subagent (`.claude/agents/pr-reviewer.md`) before it is merged. Spawn it with the PR number and the PR's purpose only, not your own conclusions, so the review is independent. Fix confirmed findings on the PR branch, and have the fix commits reviewed again before merging.
